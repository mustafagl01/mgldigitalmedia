# Website Builder

Act as a thin orchestrator for premium website builds. Drive the project from brief to buildable
spec without duplicating lower-level implementation skills.

Keep the workflow controlled:
- Start with discovery, not code.
- Pause for approval after the blueprint/spec.
- Only request AI media generation when the concept actually needs it.
- Inspect the repo before deciding whether to scaffold, extend, or patch.
- Treat mobile design as mandatory, not a later polish pass.
- Do not settle for generic "AI slop" aesthetics; commit to a distinct visual direction.

## Workflow

### Phase 1: Discovery Interview

Start by collecting the minimum information needed to shape the project:
- Business, product, or campaign name
- Offer and target audience
- Primary conversion goal
- Site shape: one-page landing page, multi-section marketing site, or richer product site
- Brand direction: tone, visual references, preferred colors, existing design system
- Available inputs: copy, logo, photos, product renders, screenshots, live site, Figma, repo
- Whether the project needs a dramatic scroll-driven hero or can use standard premium media

Do not write code in this phase. If the user asks for a website but has no useful inputs, gather
the brief first and then propose the simplest path that can still produce a convincing result.

### Phase 2: Blueprint and Approval

Once discovery is complete, produce a concise project blueprint artifact. The blueprint should be
easy to approve and specific enough to implement without re-deciding the basics.

Include:
- Project summary and audience
- Success criteria and primary CTA
- Information architecture and section plan
- Visual system direction: typography, color palette, layout character, interaction style
- Visual atmosphere notes: background treatment, motion language, texture/depth strategy, and whether the concept should feel editorial, technical, cinematic, or minimal
- Mobile behavior plan: how hero, navigation, cards, forms, and dense sections collapse or restack on small screens
- Asset plan: existing assets vs AI-generated assets
- Technical approach: whether to extend an existing app or scaffold a new frontend
- Whether scroll-stop media is justified, and if so, what the hero concept will be

Present the blueprint in chat and explicitly ask the user to approve or adjust it before moving on.

### Phase 2.5: Competitor Scraping & Content Synthesis

If the user provides competitor URLs or specifies a niche industry:
- Automatically use `read_url_content` or similar tools to extract and analyze top competitor websites.
- Extract their best content strategies, industry-specific terminology, service breakdowns, and trust signals (e.g., "Family-run", "Areas covered", certifications).
- Synthesize this research into highly authoritative, conversion-optimized copywriting for the new website.
- NEVER leave a website "empty" or relying solely on flashy animations. Ensure deep, meaningful text sections (Detailed Services, How We Work, Local SEO targets) are drafted to build genuine trust before coding the layout.

### Phase 3: Asset Path Decision

Choose the lightest path that fits the brief.

If the project needs a scroll-driven or highly cinematic hero:
- Route to the prompt-generation workflow for the required start-state, end-state, and motion prompts
- Tell the user exactly what assets are needed and in which format
- Wait until the required media or source files are available before promising implementation

If the project already has usable branding and media:
- Reuse them
- Do not force AI-generated prompts or video workflows

If the project does not need scroll-stop media:
- Continue with a standard premium frontend path
- Focus on layout, hierarchy, copy structure, trust signals, and CTA quality

When relevant, rely on these existing skills rather than duplicating them:
- `scroll-stop-builder` for frame-sequence scroll websites
- `3D Website Asset Generator` for prompt generation
- `seo-strategy` for optional SEO finishing work

### Phase 4: Implementation Preparation

Before changing code:
- Inspect the repository structure
- Identify the framework, routing model, styling system, and build tooling
- Decide whether to scaffold a new app, extend an existing app, or patch a narrow area
- Confirm any missing blockers such as required assets, missing content, or absent environment setup

Do not assume Next.js by default. Use the stack already present when one exists. Only scaffold a new
project when the repo is empty, mismatched to the task, or the user clearly wants a fresh build.

If a fresh premium frontend must be scaffolded and no stack is imposed:
- Prefer Next.js App Router, Tailwind CSS, and CSS custom properties as the baseline
- Prefer Framer Motion for component-level motion
- Add GSAP, Lenis, or React Three Fiber only when the concept clearly benefits and the performance budget allows it

### Phase 5: Implementation Guidance

When implementation begins:
- Preserve established design systems and component patterns when they already exist
- Otherwise define an intentional visual system instead of falling back to generic defaults
- Favor strong typography, clear CTA hierarchy, and responsive layouts
- Use distinctive typography; avoid defaulting to Inter, Roboto, Arial, Open Sans, Lato, or system-font stacks
- Use CSS variables and a committed palette with clear dominant tones; avoid generic purple-on-white gradients and interchangeable SaaS styling
- Create atmosphere with gradients, textures, glow, pattern, or layered depth instead of flat backgrounds
- Use a small number of high-impact motion moments rather than scattering weak micro-interactions everywhere
- Design mobile-first by default: stack content cleanly, preserve CTA visibility, size text and spacing intentionally, and avoid hover-only interactions
- For scroll-heavy or cinematic sections, define a mobile-safe fallback or simplified layout before shipping
- For `<canvas>` image-sequence sections, use screen-aware scaling logic: prefer `Math.min`/contain behavior on tall mobile screens to prevent destructive side-cropping, and `Math.max`/cover behavior on wider desktop screens
- For scroll-driven builds, hand off the detailed frame extraction and canvas behavior to the
  dedicated scroll-stop skill rather than re-explaining its internals
- For content-heavy marketing pages, structure trust, proof, benefits, objections, and contact
  paths before polishing decorative details
- Build mobile layouts concurrently with desktop layouts; do not defer them to a cleanup pass

If the user has not yet approved the blueprint or supplied required assets, do not skip ahead into
full implementation.

### Phase 6: Polish and SEO

Before calling the project complete, verify:
- Semantic structure and heading hierarchy
- Core metadata and share-preview basics when applicable
- Mobile responsiveness
- Touch usability on real mobile breakpoints, including buttons, cards, sticky sections, and form controls
- Reasonable performance for the chosen media strategy
- No unnecessary motion, dependencies, or sections that dilute conversion

Use the SEO skill as optional finishing guidance, not a mandatory full-site audit on every build.

## Guardrails

- Do not trigger for small spacing fixes, copy edits, or routine maintenance.
- Do not force a scroll-animation concept onto every website brief.
- Do not mention tools or actions that are not actually available in the environment.
- Do not promise implementation until the project shape and asset path are locked.
- Do not treat desktop completion as sufficient; every shipped section must have an intentional mobile layout.
- Do not force 3D, GSAP, Lenis, or dark-mode-first styling onto every project; use them when the brief and repo justify them.
- Keep the master skill lean; rely on downstream skills for specialized execution details.
